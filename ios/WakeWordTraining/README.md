# Jarvis wake-word training for AD Glasses

Jarvis is the assistant identity and production wake phrase for AD Glasses.

The iOS runtime and Python training environment are intentionally pinned to LiveKit WakeWord commit
`95448a7559c453fcd87645bd67b247ffb45f85b0`.

## Pronunciation

**Jarvis** is two syllables: **JAR-vis**. Keep the training target as the normal spelling `jarvis`; the hyphenated form is only a pronunciation note.

Before the production run:

```sh
espeak-ng --ipa -q -v en-us "jarvis"
espeak-ng -v en-us "jarvis"
```

Listen to the pronunciation. The guarded runner also prints the IPA during preflight.

## Environment

Production training needs Python 3.11+, `espeak-ng`, FFmpeg, the LiveKit training extras, substantial runtime, and significant free disk.

```sh
brew install python@3.11 uv espeak-ng ffmpeg portaudio
uv venv --python 3.11 .venv
uv pip install --python .venv/bin/python \
  "livekit-wakeword[train,eval,export] @ git+https://github.com/livekit/livekit-wakeword@95448a7559c453fcd87645bd67b247ffb45f85b0"
```

If `data/` already contains the Piper model, backgrounds, RIRs, ACAV100M training features, and validation features from the previous wake-word work, keep it. Those assets are phrase-independent and reusable.

For a fresh checkout or missing shared assets:

```sh
.venv/bin/livekit-wakeword setup --config jarvis.yaml
```

## Why this repository uses `train_jarvis.py`

Do **not** use `livekit-wakeword augment jarvis.yaml` or `livekit-wakeword run jarvis.yaml` for the production Jarvis run at the pinned revision.

The pinned LiveKit commit introduced configurable ONNX `SessionOptions` in feature extraction, but its CLI call sites still invoke the older one-argument extraction function. A clean installation can therefore fail when `augment` reaches feature extraction.

The pinned Piper generator also permits a failed TTS batch to be skipped while advancing the clip index. An isolated failure can leave missing `clip_######.wav` files even though generation later exits successfully. Upstream resume logic counts existing files, so it cannot reliably repair a hole in the middle of a split.

`train_jarvis.py` keeps the pinned LiveKit implementation but guards those edges. It:

- verifies the installed LiveKit Git revision is exactly the project pin;
- verifies Piper, ACAV100M training/validation features, backgrounds, RIRs, pronunciation, and free disk;
- generates all six production splits and requires contiguous clip indices;
- detects an isolated skipped TTS batch, truncates from the first gap, and regenerates the tail with bounded retries;
- runs all three augmentation rounds and verifies every expected augmented clip exists;
- invokes feature extraction with the correct `SessionOptions` signature for the pinned revision;
- verifies exact feature-array shapes before training;
- removes stale `.pt`, `.onnx`, eval, metrics, and feature artifacts before rebuilding derived data;
- starts the full three-phase classifier training only after all checks pass;
- deliberately stops after training so export/evaluation remain explicit.

## Production configuration

`jarvis.yaml` is intentionally production scale:

- 25,000 positive training originals
- 5,000 positive validation originals
- 25,000 / 5,000 adversarial-negative originals generated by LiveKit
- 2,000 / 500 standalone background originals
- 3 augmentation rounds
- medium conv-attention classifier
- 100,000 phase-1 steps + 10,000 phase-2 + 10,000 phase-3 = **120,000 optimizer steps**
- target false positives: 0.10/hour

The TTS batch size is **25**. LiveKit's generic production example uses 50 for sufficiently large GPUs, but this project previously encountered resource/stability trouble at 50. Batch 25 trades generation throughput for headroom; it does not reduce the requested sample counts.

With 3 augmentation rounds, complete feature extraction should produce:

```text
positive_features_train.npy          (75000, 16, 96)
positive_features_test.npy           (15000, 16, 96)
negative_features_train.npy          (75000, 16, 96)
negative_features_test.npy           (15000, 16, 96)
background_noise_features_train.npy   (6000, 16, 96)
background_noise_features_test.npy    (1500, 16, 96)
```

The guarded runner requires those exact shapes before it starts training.

## Recheck before the overnight run

From `ios/WakeWordTraining`:

```sh
.venv/bin/python train_jarvis.py --preflight-only
```

Preflight fails rather than guessing if the pinned package, shared datasets, TTS artifacts, audio assets, or minimum free disk are missing.

For the first production Jarvis run, start with a clean phrase-specific output directory:

```sh
caffeinate -dimsu .venv/bin/python train_jarvis.py --fresh
```

`--fresh` removes only `output/jarvis`; it does **not** delete the reusable `data/` directory or your old Hey-A-D output.

If generation is interrupted, rerun without `--fresh`:

```sh
caffeinate -dimsu .venv/bin/python train_jarvis.py
```

The generation stage can repair/resume partial Jarvis splits. Training itself does not have a durable cross-process phase-resume checkpoint in this LiveKit revision, so if the process dies during the 120,000 optimizer steps, the training stage must be run again.

## Post-training export and evaluation

After `train_jarvis.py` finishes successfully:

```sh
.venv/bin/livekit-wakeword export jarvis.yaml
.venv/bin/livekit-wakeword eval jarvis.yaml
```

These two commands do not use the broken feature-extraction CLI path. They operate on the already-trained `.pt` model and already-validated feature files.

Expected artifacts include:

```text
output/jarvis/jarvis.pt
output/jarvis/jarvis.onnx
output/jarvis/jarvis_eval.json
output/jarvis/jarvis_det.png
```

Then bundle only the evaluated classifier:

```sh
python3.11 bundle_evaluated_model.py
```

The bundler refuses to package Jarvis unless evaluation reports all of the following:

- at least 90% recall at the calibrated optimal threshold;
- no more than 0.10 false positives/hour at that threshold;
- at least 15,000 held-out positive feature examples (5,000 originals × 3 augmentation rounds);
- at least 15 hours of negative validation, which ensures the shared general-negative validation set was included;
- a valid optimal threshold strictly between 0 and 1.

On success it copies `output/jarvis/jarvis.onnx` to `ADGlasses/Resources/WakeWords/jarvis.onnx`, removes a legacy `hey_a_d.onnx` if one remains, computes the SHA-256, and rewrites `manifest.json` with the evaluated threshold and metrics.

Do not commit `data/`, `output/`, or a toy classifier. Commit the evaluated `jarvis.onnx` and generated `Resources/WakeWords/manifest.json` together after bundling.
